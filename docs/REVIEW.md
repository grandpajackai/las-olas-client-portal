# Product and mobile UX review

Review opened **October 13, 2026**. This is an evidence-based acceptance review for a public **browser feedback preview** of the Las Olas portal. It is not a claim of perfection, WCAG certification, native device acceptance, or production readiness. The iPhone/Android source remains part of the project; signed binaries and store distribution have separate acceptance requirements in [QA.md](QA.md) and [PRODUCTION.md](PRODUCTION.md).

## Product standard

An owner should be able to answer four questions quickly: **What needs my attention? What care was completed? What happens next? How do I reach the team?** A manager should see what needs a decision, review, assignment, or scheduling without reconstructing the fleet one vessel at a time. A field user should record an observation without losing work, confusing an unchecked item with a pass, or accidentally publishing private notes.

Keep the established ink/deep teal, ivory, darker gold, yacht photography, Cormorant Garamond display typography, and DM Sans interface typography. Increase clarity and interaction comfort within that identity. Decorative imagery and editorial headings should support the care record rather than push decisions and dates far below the first phone screen.

## Research informing this review

- Apple describes tab bars as navigation between top-level sections, with visible labels, stable access, and preserved context. This supports a compact, complete navigation map with a clear selected destination when entering Schedule or Approvals. It does not require copying a specific native visual treatment into the browser preview. [Apple tab bars](https://developer.apple.com/design/human-interface-guidelines/tab-bars?changes=la_11)
- Android recommends touch targets of at least 48 × 48 dp. The shared Button adopts **48 logical units**; the browser preview deliberately uses **44-unit chips** as a compact web interaction choice. Native controls must still be measured against the 48 dp recommendation on devices. Web WCAG 2.2 AA's target-size criterion has a different 24 CSS pixel minimum and exceptions; meeting it does not establish native accessibility acceptance. [Android accessibility](https://developer.android.com/guide/topics/ui/accessibility/views/apps-views), [W3C target size](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum)
- W3C calls for ordinary text contrast of at least 4.5:1, with a 3:1 allowance for sufficiently large text. Its reflow guidance expects ordinary horizontal content to fit a 320 CSS pixel width without two-direction scrolling. Use these as measurable web checks, alongside 200% text/zoom checks. [W3C contrast](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html), [W3C reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html)
- W3C guidance supports identifying the field and explaining errors in text, and exposing displayed success/wait/error status to assistive technology without forcing focus into every routine update. A transient success-styled toast should not carry the only explanation of a failed approval or save. [W3C error identification](https://www.w3.org/WAI/WCAG22/Understanding/error-identification.html), [W3C status messages](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html)
- YACHTWAVE presents the branded owner portal around what was done, when, by whom, and what comes next; its fleet view emphasizes readiness and due work. This validates a care/status summary and a management queue ahead of decorative content. These are reference patterns, not independent evidence of that product's usability. [YACHTWAVE Fleet](https://www.yachtwave.com/fleet)
- Vessel Vanguard describes preventive schedules, work orders, photos/notes, equipment history, and offline work followed by synchronization. The useful pattern here is continuity from request to completed evidence, with explicit offline limits. Las Olas should only claim its implemented text queue; the reference product's broader offline claims do not establish parity. [Vessel Vanguard maintenance](https://vesselvanguard.com/solutions/maintenance/)
- GitHub documents Pages as static hosting for HTML, CSS, and JavaScript, available for public repositories with GitHub Free. That fits a free public browser feedback preview using browser-local demonstration data. Pages does not run the project's Node/SQLite API; the preview must not imply a live shared backend or native distribution. [What is GitHub Pages?](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages)

The initial contrast figures were computed from the source hex colors using relative luminance. They describe those exact opaque color pairs, not text placed over variable photography. Photo overlays and disabled/non-text controls need their own rendered review.

## Public feedback preview boundary

The planned public host is a **static browser demonstration with data isolated in each browser**. Its accounts, roles, actions, and authorization behavior simulate the product; they are not a hosted shared client/staff service or a substitute for the separately tested local API's server-enforced authorization. Testers should use fictional data only. The preview should state where edits persist, how to reset them, and whether a reload preserves them.

Do not describe a static browser preview as an App Store/Google Play app, a deployed production backend, or operational yacht monitoring. Live hosting, production identity/delivery/storage, signed binaries, physical-device QA, store submissions, support ownership, backups, privacy, and remaining dependency risk retain their existing release requirements.
